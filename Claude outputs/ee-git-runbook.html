Facilitator runbook · electrical-lfs-sandbox

Getting EE work into the repo

Thirty minutes of guided hands-on, then thirty minutes of help. One goal: everybody ends the hour having put a file into a shared repo, on a properly named branch, through a pull request.

Slot
First of two presenters
Format
30 min guided · 30 min help
Room
~6–20 EEs, mixed skill
Repo
electrical-lfs-sandbox
–10 min

Before you join

Ten minutes of setup that buys back five minutes of fumbling on camera.

Decide before you start

Are you demonstrating each command first and then waiting, or typing in lockstep with them? Demo-then-wait is better. They watch you do it once, then do it themselves while you watch the chat. Typing together means the slowest person sets your pace and you can't see who's stuck.

0:00 – 0:02

Open

Set the goal, defuse the anxiety, give the fast people a job.

Say — the goal

"By the end of the next thirty minutes, every one of you will have put a file into a shared repo, on a branch with a proper name, through a pull request. That's the whole goal. If you already know how to do that, stick around anyway — the naming rules are ours, not GitHub's."

Say — the escape hatch

"If your Git Bash isn't working, don't panic and don't spend this half hour fighting it. You can do this entire exercise in the browser instead. Drop a note in chat and keep moving — I'll find you afterward."

Say — recruit the experts

"Some of you have used Git for years and I'm going to go slower than you need. If you're ahead, watch the chat and help whoever's stuck. That's genuinely the most useful thing you can do for the next half hour."

Say — the repo is public

"One thing before we start: this practice repo is currently public, meaning anyone on the internet can read it. So when you make your file, put your name and your market and nothing else. No customer names, no part numbers, no project details."

"That habit — asking 'should this be public?' before you commit — is worth more than anything else I'm going to show you today."

Why the 'help your neighbor' line matters

It converts your biggest disruption risk into your support staff, and it gets your conventions taught out loud by the people most likely to ignore them.

0:02 – 0:05

Why we're doing this

Three minutes. Name the real problem, then stop — don't lecture.

Say

"Two things are happening right now. First, a lot of EE work never makes it into the repo at all — it lives on somebody's laptop. Second, the work that does make it in often lands in one shared branch where nobody can tell whose changes are whose, and we step on each other."

"The fix is small. Your work goes on a branch. The branch has a name that says which market and what you're doing. It comes back to main through a pull request. That's it — that's the entire ask."

Show, briefly

Put the sandbox's branch list on screen. Right now it's nearly empty — say that by the end of the half hour it'll have everyone's name in it, and that that is what the real repo should look like.

Resist

Don't get drawn into why the current state happened, or whose fault it is. Somebody will offer a reason. Acknowledge it in one sentence and move — this block is three minutes and it's the easiest one to blow.

0:05 – 0:10

Branch naming rules

Slides here. Five minutes, four ideas. They need this before they can do step 3 of the exercise.

# the shape <market>/<topic> # real examples ag/pump-ctrl-rev-b dozer/harness-rework compactor/vibe-motor-swap adt-wt/pump-ctrl/sensor-cal ← optional subtopic
Rule 1 — the one they'll remember

Never touch the Shift key.

Every character in a branch name is unshifted: lowercase letters, the hyphen, the slash. If you pressed Shift, you typed it wrong. Why: GitHub treats upper and lower case as different branches; Windows doesn't. Mix them and you get two branches on the server that your PC can't tell apart — and tab-completion stops working.

Rule 2 — the one that bites

A name is a branch OR a folder of branches. Never both.

Git stores each branch as a real file on disk. If ag/pump-ctrl exists as a branch, ag/pump-ctrl/sensor-cal cannot be created — you can't have a file and a folder with the same name. So if you think you'll want sub-branches under a topic, don't create the bare topic branch.

Rule 3

release-candidate is reserved.

Each market's <market>/release-candidate is where that market collects work for internal review before it's PR'd to main. Don't use that name for ordinary work.

Rule 4 — the payoff

A good branch name writes your PR title for you.

Show them: the setup/seed-files branch produced a PR titled "Setup/seed files." GitHub capitalizes it and swaps the hyphens for spaces, free. A branch called stuff2 produces a PR called "Stuff2." This is the moment the convention stops feeling like bureaucracy.

Then narrow it for today

Tell them that for this exercise everyone uses one shape instead: training/lastname-firstname — e.g. training/smith-jane.

Say why: "I don't want fifteen practice branches cluttering up the market namespaces, and I don't want anyone stuck deciding which market they're in before they can start. The rules are identical — lowercase, hyphens, slash, no Shift key. Only the first segment changes."

Say — the war story (60 seconds, optional but good)

"In the real repo we have a branch called blitz. Blitz is also a market. Which means nobody can create blitz/anything until we rename it — you get a cryptic error about not being able to lock a ref. That's rule 2, and it's not hypothetical."

0:10 – 0:27

The exercise: sign the guestbook

Seventeen minutes. Demo each step, then wait. git status between steps is the metronome — it's not extra work, it's the thing that makes the rest learnable.

The shape of this block

git status is the spine. It runs after every state change, and each time it prints something different — untracked, staged, ahead by one, up to date. That's not repetition, that's the lesson: Git tells you where you are, and usually what to do next.

Step 4 sets up step 5. Git literally prints use "git add <file>..." to include in what will be committed. Let Git introduce the command rather than introducing it yourself — it's the moment they learn to read the output instead of following a script.

Don't skip git add. A brand-new file cannot be committed without it, and git commit -a won't rescue you — it only picks up changes to files Git already tracks. Skip it and fifteen people hit "nothing added to commit but untracked files present" at the same moment.

  1. refresh the clone

    $ cd /c/GitLocal/electrical-lfs-sandbox $ git pull

    Don't skip this. Anyone who cloned before this morning has the old EXERCISE.md — different branch shape, wrong default branch. One git pull fixes it.

  2. where am I?

    $ git status

    Say: "This is the command you'll run more than any other. Read the output — it's written for humans, and it usually names the command you want next. When something feels wrong, run this first."

    Everyone sees On branch master, nothing to commit, working tree clean.

  3. branch and switch

    $ git checkout -b training/hopper-eric

    They substitute their own lastname-firstname. -b means "create it"; checkout switches onto it.

    Say: "You've just made yourself a private workspace. Nothing you do from here touches anyone else until you push it and open a pull request."

    Checkpoint: ask everyone to paste their branch name in chat. Thirty seconds, tells you who's with you, and catches naming mistakes before they're pushed.

  4. do the "work"

    $ touch guestbook/EricHopper.txt $ notepad guestbook/EricHopper.txt

    Say: "On a real day this is where you'd do your actual engineering. Today it's a text file with your name on it."

    Name and market only — the repo is public. Save, close Notepad.

    If asked why your filename has capitals: "the no-Shift rule is for branch names. Filenames just need to be sensible." Say it confidently and move on.

  5. what did Git notice?

    $ git status

    File appears under Untracked files.

    Say: "Git can see your file, but it isn't watching it yet — it doesn't assume everything in the folder belongs in the repo. Now read the line underneath. It's telling you the next command."

  6. do what Git just told you

    $ git add guestbook/EricHopper.txt

  7. check again

    $ git status

    Now under Changes to be committed.

    Say — why two steps: "With one file this feels like busywork. On a real change you might touch six files and only want three of them in this commit. add is you choosing what goes in. commit is you saving that choice."

  8. commit

    Say this BEFORE they type it

    "You must include the -m and the message in quotes. If you forget, Git opens a full-screen editor called vim and you will not be able to figure out how to get out of it. If that happens: press Esc, then type :q! and hit Enter."

    Have Esc :q! Enter on a slide. Somebody will need it.

    $ git commit -m "Added my name to the guestbook"

    EXERCISE.md puts the warning above the command too — read it in that order so the handout and the screen agree.

  9. check again

    $ git status

    Clean tree, and "ahead of 'origin/...' by 1 commit."

    Say: "Saved on your machine. Still nobody else can see it. That word ahead is Git telling you that you have something the server doesn't."

  10. push

    $ git push -u origin training/hopper-eric

    Say: "Now it's on GitHub. -u links your branch to the server's copy, so next time plain git push is enough. Look at the output — GitHub prints you a link for opening a pull request."

  11. check one more time

    $ git status

    "up to date with 'origin/...'" — local and server match. The round trip is closed.

  12. open the PR in the browser

    Click the printed link, or use Compare & pull request on the repo. Base master, compare their branch, Create pull request.

    Point out the auto-generated title — that's rule 4 paying off in real time.

    Say: "If you're done, help someone near you, or look at the 'Done early?' list at the bottom of EXERCISE.md. I'll merge them all in a few minutes."

0:27 – 0:30

Merge live, then hand off

The payoff moment. Batch it — don't merge continuously while you're also teaching.

Share the Pull requests page. Work down the list approving and merging. It should be a few seconds each — a new file that conflicts with nothing.

If a PR is wrong — this is a gift, not a problem

Off-convention branch name, wrong base branch, file in the wrong place. Say it out loud and why, then let them fix it. Thirty seconds of real feedback on a real PR teaches more than the whole rules section. You are the reviewer; showing the room what review looks like is the lesson.

Say — the honest bit about main

"You'll notice none of you could push straight to master — it's protected, everything comes through a PR. That's true in the real repo for everyone including me. In this sandbox I have a bit more control, because somebody had to set it up."

Say — what's coming next time

"Things I deliberately skipped today, which we'll cover in future sessions: how LFS handles the Danfoss files and why they look like tiny text files sometimes; cloning only your own market's folder instead of all ten; what to do when two people edit the same binary and Git can't merge it; and file locking to stop that happening in the first place."

Then hand off: "The files you'll actually be putting on these branches are what's coming up next — over to you."

0:30 – 1:00

Office hours

Unstructured by design. Have a triage order so you don't spend all of it on one person.

  1. Anyone who never got a working clone. Highest value — they can't participate at all until this is fixed. Credential problems first (see traps below).
  2. Anyone whose PR didn't land. Usually a push that failed or a branch made off the wrong base.
  3. Anyone who finished and wants more. Point them at CONTRIBUTING.md and the release-candidate flow. Let them talk to each other.
  4. The "how does this apply to my actual work" conversation. This is the most valuable thirty minutes available to you if the first three are clear.
Ask before people drop off

"What's the thing about our repo that most makes you not want to use it?" Write the answers down. That's next month's session, chosen by the room instead of by you.

reference

Traps, and the one-line fixes

Keep this visible. When somebody pastes an error in chat, match it here first.

Stuck in a full-screen editor after git commit

They forgot -m. Press Esc, type :q!, Enter. Then redo the commit with -m "message".

Unable to create '.git/index.lock': File exists

A previous git command was interrupted. Safe fix, as long as nothing else is running:

$ rm -f .git/index.lock

fatal: not a git repository

They're in the wrong folder. pwd shows where they are; they want /c/GitLocal/electrical-lfs-sandbox. Remind them Git Bash writes C:\ as /c.

Repository not found, or a 403, with no sign-in prompt

Wrong GitHub account cached — common for contractors with a second account. Clear it and re-authenticate:

$ printf "protocol=https\nhost=github.com\n" | git credential reject

If they need both accounts side by side:

$ git config --global credential.https://github.com.useHttpPath true

SSL certificate problem: unable to get local issuer certificate

Corporate HTTPS inspection on a managed machine — browsers work, Git doesn't. They need their IT's CA bundle path:

$ git config --global http.sslCAInfo "/c/path/to/ca-bundle.crt"
Never

Do not let anyone "fix" this with http.sslVerify false. It appears to work and it disables certificate checking on a machine somebody else governs. Park them on the browser fallback instead.

cannot lock ref when creating a branch

Rule 2. A branch already exists with a name that would have to be a folder. Pick a different name.

Anything you can't fix in two minutes

Browser fallback. On GitHub: open a file → pencil icon → edit → "Create a new branch for this commit and start a pull request" → name it per convention → commit. Branch, commit and PR, no terminal at all. They miss the command-line practice but not the workflow, and they're participating instead of watching.
